## 증상부터

로그인 후 원래 페이지로 돌아가는 리다이렉트를 붙였다. 주소창에 이런 게 뜬다.

```
/login?next=https%253A%252F%252Fexample.com%252Fdocs
```

`%25`가 눈에 띄면 이중 인코딩이다. 파일 다운로드 링크에서 파일명이 `report%20final.pdf`로 그대로 보이거나, 검색어의 공백이 `+`로 남아 결과가 0건인 것도 같은 계열이다.

## %25가 신호다

퍼센트 인코딩은 바이트를 `%XX`로 바꾼다. 공백은 `%20`이다. 그런데 **`%` 자체도 인코딩 대상**이고, `%`의 인코딩 결과가 `%25`다.

이미 인코딩된 문자열을 한 번 더 인코딩하면 앞의 `%`가 `%25`로 바뀐다.

| 원본 | 1회 인코딩 | 2회 인코딩 |
|------|-----------|-----------|
| (공백) | `%20` | `%2520` |
| `/` | `%2F` | `%252F` |
| `&` | `%26` | `%2526` |
| `?` | `%3F` | `%253F` |
| `한` | `%ED%95%9C` | `%25ED%2595%259C` |

**`%25`가 보이면 인코딩이 한 번 더 걸린 것이다.** 디코딩을 한 번 하면 `%20`이라는 다섯 글자 문자열이 나오고, 두 번 해야 공백이 된다.

몇 번 겹쳤는지는 반복 디코딩으로 센다.

```bash
python3 -c "
from urllib.parse import unquote
s = '%2520hello%2520world'
for i in range(4):
    print(i, s)
    s2 = unquote(s)
    if s2 == s: break
    s = s2
"
```

값을 바로 확인하려면 [URL 인코더/디코더](/tools/net/url-encoder/)에 넣고 디코딩을 반복해보면 된다. 원문이 나올 때까지 몇 번 눌러야 하는지가 곧 인코딩 횟수다.

## encodeURI와 encodeURIComponent

자바스크립트에서 가장 흔한 원인이다. 둘은 인코딩하는 문자 집합이 다르다.

| 함수 | 예약 문자(`: / ? # & = + $ , @`) | 용도 |
|------|------------------------------|------|
| `encodeURI` | **보존한다** | URL 전체를 인코딩할 때 |
| `encodeURIComponent` | **인코딩한다** | 파라미터 값 하나를 인코딩할 때 |

파라미터 값에 `encodeURI`를 쓰면 값 안의 `&`와 `=`가 살아남아 쿼리스트링이 쪼개진다.

```js
const next = 'https://example.com/a?b=1&c=2';

`/login?next=${encodeURI(next)}`
// /login?next=https://example.com/a?b=1&c=2
// → 서버는 next=https://example.com/a?b=1 과 c=2 두 파라미터로 읽는다

`/login?next=${encodeURIComponent(next)}`
// /login?next=https%3A%2F%2Fexample.com%2Fa%3Fb%3D1%26c%3D2   ✓
```

반대로 **이미 `encodeURIComponent`를 거친 값에 또 `encodeURI`를 씌우는 것**이 `%2520`을 만드는 전형적인 경로다. 프레임워크의 라우터나 HTTP 클라이언트가 자동으로 인코딩하는데 수동으로 한 번 더 하는 경우가 대부분이다.

규칙은 하나다. **인코딩은 값이 URL에 들어가기 직전 한 번만.**

## 쿼리의 +와 경로의 +

같은 `+`가 위치에 따라 다르게 해석된다.

| 위치 | `+`의 의미 | 공백 표현 |
|------|-----------|----------|
| 쿼리스트링 (`application/x-www-form-urlencoded`) | 공백 | `+` 또는 `%20` |
| 경로(path) | 리터럴 `+` | `%20`만 |
| 폼 전송 본문 | 공백 | `+` |

`C++ tutorial`을 쿼리로 넘길 때 `+`를 인코딩하지 않으면 서버가 `C  tutorial`로 읽는다. 반대로 경로에 있는 `a+b.pdf`를 쿼리로 옮기면 `a b.pdf`가 된다.

파이썬은 함수가 분리돼 있다.

```python
from urllib.parse import quote, quote_plus

quote('C++ tutorial')        # 'C%2B%2B%20tutorial'   경로용
quote_plus('C++ tutorial')   # 'C%2B%2B+tutorial'     쿼리용
```

셸에서 값 하나만 빠르게 인코딩할 때는 jq가 편하다.

```bash
printf '%s' 'C++ tutorial' | jq -sRr @uri
# C%2B%2B%20tutorial
```

## 어디서 겹치는가

| 지점 | 겹치는 방식 |
|------|-----------|
| 프레임워크 자동 인코딩 + 수동 인코딩 | 라우터·HTTP 클라이언트가 이미 처리한 값을 또 감쌈 |
| 리버스 프록시 | 프록시가 한 번 디코딩해 백엔드에 넘기는데 백엔드도 디코딩 기대 |
| 리다이렉트 체인 | `Location` 헤더를 재조립하면서 이미 인코딩된 URL을 다시 인코딩 |
| 중첩 파라미터 | `redirect_uri` 안에 또 쿼리가 들어가는 OAuth 흐름 |
| 로그·모니터링 | 수집기가 URL을 인코딩해 저장 → 그 값을 그대로 재사용 |

리다이렉트 쪽이 의심되면 헤더 원문을 본다. 브라우저 주소창은 보기 좋게 디코딩해서 표시하므로 실제 바이트와 다르다.

```bash
curl -sI 'https://example.com/redirect?next=...' | grep -i '^location'
```

[HTTP 헤더 검사기](/tools/net/http-headers-checker/)로도 `Location` 원문을 그대로 확인할 수 있다.

## 서명 검증에서 특히 위험하다

웹훅 서명이나 API 서명은 문자열을 바이트 단위로 비교한다. 인코딩 형태가 다르면 내용이 같아도 불일치한다.

- 대소문자: RFC 3986은 `%2F`처럼 **대문자 hex**를 권장한다. `%2f`도 유효하지만 서명 문자열은 달라진다.
- 비예약 문자 과잉 인코딩: `~`는 인코딩하지 않아도 되는데 `%7E`로 보내는 구현이 있다.
- 파라미터 순서: 정렬 규칙이 서명 스펙에 명시돼 있는지 확인한다.

서명 전에 정규화 규칙을 문서와 맞추고, 그 규칙을 양쪽 코드에 똑같이 박아두는 게 유일한 해법이다. "왜 서명이 가끔 틀리지"의 상당수가 이 문제다.

## 진단 순서

1. `%25`가 있는지 본다. 있으면 이중 인코딩 확정이다.
2. 반복 디코딩으로 몇 겹인지 센다.
3. 값이 URL에 합쳐지는 코드 경로를 따라가며 인코딩 호출을 전부 찾는다. 둘 이상이면 하나만 남긴다.
4. 프록시나 게이트웨이를 지나면 그 구간의 디코딩 동작을 확인한다.
5. 공백이 `+`로 나오는지 `%20`으로 나오는지 보고 경로용/쿼리용 함수를 맞춘다.

## 정리

- `%25`는 인코딩이 한 번 더 걸렸다는 신호다. `%2520`은 공백이다.
- 파라미터 값은 `encodeURIComponent`, URL 전체는 `encodeURI`. 값에 `encodeURI`를 쓰면 쿼리가 쪼개진다.
- 인코딩은 URL에 넣기 직전 딱 한 번만 한다.
- `+`는 쿼리에서 공백, 경로에서 리터럴이다. 파이썬은 `quote_plus`와 `quote`로 나뉜다.
- 리다이렉트 문제는 주소창 말고 `Location` 헤더 원문으로 확인한다.
- 서명 검증에는 대소문자 hex와 과잉 인코딩까지 정규화 규칙을 맞춘다.
