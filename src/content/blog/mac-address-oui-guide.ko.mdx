## 시작은 늘 같다

공유기 관리 페이지를 열었는데 연결된 장비가 생각보다 많다. 이름은 `unknown`, 보이는 건 IP와 MAC 주소뿐. 우리 집 기기가 맞는지, 옆집이 비밀번호를 뚫은 건지 이것만으로 판단해야 한다.

사무실이면 더 자주 겪는다. 스위치 포트에 뭔가 꽂혀 있는데 자산 목록에 없다. NAC 도입 전 실사, 침해 대응 초동 분석, IP 충돌 추적 — 전부 "이 MAC이 어떤 장비냐"에서 시작한다.

MAC 주소만으로 장비를 특정할 수는 없다. 하지만 **제조사까지는 즉시 나온다.** 그리고 제조사만 알아도 후보가 확 줄어든다. `Espressif`면 IoT 기기(스마트 플러그, 전구류), `Azurewave`면 노트북/태블릿 무선 모듈, `Hon Hai`(Foxconn)면 조립 기기 쪽이다.

## MAC 주소는 반으로 쪼개진다

MAC 주소는 48비트, 표기로는 `A4:83:E7:12:34:56` 같은 6바이트다. 구조는 정확히 절반씩 나뉜다.

| 구간 | 이름 | 의미 |
|------|------|------|
| 앞 3바이트 (`A4:83:E7`) | OUI | IEEE가 제조사에 판매한 식별자 |
| 뒤 3바이트 (`12:34:56`) | NIC 부분 | 제조사가 장비마다 부여한 일련번호 |

OUI(Organizationally Unique Identifier)는 IEEE Registration Authority가 관리하고, 제조사가 돈 주고 사는 블록이다. 애플·삼성 같은 회사는 수백 개씩 갖고 있다. 이 매핑이 공개 레지스트리라서 조회가 가능한 것이다.

블록 크기는 세 종류가 있다. MA-L(24비트 프리픽스, 주소 1,600만 개), MA-M(28비트), MA-S(36비트). 소규모 제조사가 MA-S를 사면 앞 3바이트가 같아도 회사가 다를 수 있다 — 조회 결과가 이상하게 느껴질 때 종종 이 케이스다.

조회 자체는 [MAC OUI 조회기](/tools/net/mac-oui-lookup/)에 붙여넣으면 끝난다. 콜론이든 하이픈이든 점(`a483.e712.3456`, Cisco 표기)이든 구분자는 알아서 처리된다. IEEE MA-L/MA-M/MA-S 레지스트리 전체를 통합해 두었다.

## MAC 주소를 수집하는 명령어

조회할 MAC부터 모아야 한다. 같은 L2 세그먼트에 있는 장비는 ARP 테이블에 쌓인다.

```bash
# macOS / Windows — ARP 캐시 전체
arp -a

# Linux — 최신 도구
ip neigh

# 세그먼트 전체 스캔 후 ARP 테이블 채우기 (핑 스윕)
nmap -sn 192.168.0.0/24
```

`nmap -sn`을 먼저 돌리고 `arp -a`를 보면 살아 있는 장비의 IP-MAC 쌍이 한 번에 나온다. 대역 계산이 필요하면 [서브넷 계산기](/tools/net/subnet-calculator/)로 범위를 확인하고 돌리면 된다.

주의할 점 하나. ARP는 라우터를 넘지 못한다. 다른 서브넷 장비의 MAC은 그 세그먼트 안에서 수집해야 하고, 원격에서 보이는 건 게이트웨이의 MAC뿐이다.

## 조회했는데 "등록 없음"이 나온다면

여기가 이 글의 핵심이다. 요즘 스마트폰 MAC은 조회해도 안 나오는 경우가 절반이다. 고장이 아니라 **의도된 동작**이다.

첫 옥텟의 두 번째 비트(U/L 비트)가 1이면 "로컬 관리 주소" — 제조사가 구운 주소가 아니라 소프트웨어가 만들어낸 주소라는 선언이다. 16진수로 보면 판별이 쉽다. **두 번째 자리가 2, 6, A, E면 랜덤/로컬 주소다.**

```text
X2:XX:XX:XX:XX:XX  ┐
X6:XX:XX:XX:XX:XX  │ 로컬 관리 주소
XA:XX:XX:XX:XX:XX  │ (OUI 조회 불가가 정상)
XE:XX:XX:XX:XX:XX  ┘
```

iOS는 14부터 Wi-Fi 네트워크마다 "사설 Wi-Fi 주소"를 만들고, Android도 10부터 랜덤 MAC이 기본이다. 프라이버시 보호 — 매장 와이파이가 MAC으로 동선을 추적하는 걸 막는 용도다. 그래서 공유기 목록의 `5A:xx`, `D6:xx` 같은 주소는 대부분 가족의 스마트폰이다.

운영 관점의 부작용도 있다. MAC 필터링과 고정 DHCP 임대가 이 기능 때문에 깨진다. 아이폰이 "새 장비"로 계속 등록되는 공유기라면, 해당 네트워크만 사설 주소를 끄는 게 처방이다.

## 랜덤이 아닌데 조회가 안 되는 나머지 경우

로컬 주소 패턴(2/6/A/E)이 아닌데도 못 찾는 케이스는 대체로 이 중 하나다.

- **신규 OUI**: IEEE 레지스트리는 계속 늘어난다. 조회 DB가 오래됐으면 최신 블록이 빠져 있을 수 있다.
- **MA-S 블록**: 앞 3바이트가 아니라 4.5바이트까지 봐야 제조사가 갈린다.
- **가상 MAC**: 프로토콜이 규약으로 만들어내는 주소다. 외우면 현장에서 바로 알아본다.

| 패턴 | 정체 |
|------|------|
| `00:00:5E:00:01:XX` | VRRP 가상 라우터 (XX = VRID) |
| `00:00:0C:07:AC:XX` | Cisco HSRP (XX = 그룹 번호) |
| `02:42:XX:XX:XX:XX` | Docker 컨테이너/브리지 |
| `00:50:56`, `00:0C:29` | VMware 가상머신 |
| `08:00:27` | VirtualBox 가상머신 |
| `33:33:XX:XX:XX:XX` | IPv6 멀티캐스트 (장비 아님) |
| `01:00:5E:XX:XX:XX` | IPv4 멀티캐스트 (장비 아님) |

패킷 캡처에서 `01:00:5E`나 `33:33`으로 시작하는 목적지 MAC을 장비로 착각하고 찾아 헤매는 일이 의외로 흔하다. 첫 옥텟의 최하위 비트가 1이면 멀티캐스트 — 개별 장비가 아니다.

## 정리

1. `nmap -sn` + `arp -a`로 세그먼트의 IP-MAC 쌍을 모은다.
2. [OUI 조회](/tools/net/mac-oui-lookup/)로 제조사를 붙인다. 제조사만 알아도 장비 후보는 크게 좁혀진다.
3. 두 번째 16진수가 2/6/A/E면 스마트폰 랜덤 MAC일 가능성부터 본다 — 조회 실패가 정상이다.
4. `00:00:5E`, `02:42` 같은 가상 MAC 패턴은 장비가 아니라 프로토콜이다.

MAC은 L2를 벗어나면 보이지 않고, 위조도 한 줄이면 된다(`ip link set dev eth0 address ...`). 보안 판단의 근거로는 약하지만, "이게 뭐지"의 첫 단서로는 여전히 가장 빠르다. 공인 IP 쪽 단서가 필요하면 [IP 조회](/tools/net/ip-lookup/)와 조합하면 된다.
