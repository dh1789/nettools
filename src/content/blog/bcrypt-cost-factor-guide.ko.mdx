## 증상부터

로그인 API 응답이 평소 300ms에서 3초로 늘었다. 코드는 그대로다. 서버를 옮겼거나, 컨테이너 CPU 할당을 줄였거나, 누군가 설정에서 cost를 올렸다. 동시 로그인이 몰리면 스레드 풀이 먼저 마르고 전체 요청이 밀린다.

DB 쿼리는 멀쩡한데 로그인만 느리다면 비밀번호 해싱을 의심한다.

## cost는 곱셈이 아니라 지수다

bcrypt의 cost factor는 반복 횟수의 지수다. 실제 반복은 2^cost회다.

| cost | 반복 횟수 | 상대 시간 |
|------|----------|----------|
| 10 | 1,024 | 1× |
| 11 | 2,048 | 2× |
| 12 | 4,096 | **4×** |
| 13 | 8,192 | 8× |
| 14 | 16,384 | 16× |

cost를 10에서 12로 "조금" 올린 게 4배다. 12에서 14면 16배다. 설정 파일에서 숫자 둘 차이가 응답 시간을 자릿수로 바꾼다.

절대 시간은 CPU마다 다르므로 배포 대상 하드웨어에서 직접 재는 게 유일한 방법이다.

```bash
# Python
python3 -c "
import bcrypt, time
for c in (10, 11, 12, 13):
    t = time.time(); bcrypt.hashpw(b'benchmark', bcrypt.gensalt(c))
    print(f'cost {c}: {(time.time()-t)*1000:.0f}ms')
"

# Node.js
node -e "
const b=require('bcrypt');
for (const c of [10,11,12,13]) {
  const t=Date.now(); b.hashSync('benchmark', c);
  console.log('cost '+c+': '+(Date.now()-t)+'ms');
}
"
```

값을 눈으로 확인하며 조정하려면 [BCrypt 해시 생성기](/tools/net/bcrypt-generator/)에서 cost를 바꿔가며 생성해보면 된다.

## cost를 정하는 기준

숫자를 먼저 정하지 말고 **허용 가능한 로그인 지연**에서 역산한다.

| 목표 | 권장 |
|------|------|
| 로그인 응답에 쓸 수 있는 시간 | 250ms ~ 1s |
| 그 시간에 맞는 cost | 측정해서 결정 |
| 최소선 | 10 (2026년 기준 하한) |

동시성도 같이 계산한다. 해싱 1회가 250ms면 코어 하나가 초당 4회를 처리한다. 4코어 서버에서 로그인 피크가 초당 50건이면 그 자체로 포화다. cost를 올리기 전에 이 계산을 먼저 한다.

비밀번호 해싱은 원래 느리라고 만든 함수다. 느린 게 목적이므로 "최적화"하면 안 되고, 대신 **얼마나 느릴지를 의도적으로 고르는 것**이다.

## 72바이트에서 잘린다

bcrypt는 입력을 72바이트까지만 쓴다. 그 뒤는 조용히 버린다. 앞 72바이트가 같은 두 비밀번호는 서로 통과한다.

```bash
python3 -c "
import bcrypt
a = b'A'*72 + b'-first'
b_ = b'A'*72 + b'-second'
h = bcrypt.hashpw(a, bcrypt.gensalt(10))
print(bcrypt.checkpw(b_, h))   # True — 다른 비밀번호인데 통과한다
"
```

긴 패스프레이즈를 권장하는 서비스에서 실제로 문제가 된다. UTF-8에서 한글은 글자당 3바이트라 24글자면 이미 72바이트다. 이모지가 섞이면 더 빨리 찬다.

대응은 bcrypt에 넣기 전에 고정 길이로 줄이는 것이다.

```js
import crypto from 'crypto';
// SHA-256 → base64 = 44바이트, 항상 72 이하
const pre = crypto.createHash('sha256').update(password).digest('base64');
const hash = await bcrypt.hash(pre, 12);
```

바이너리 다이제스트를 그대로 넘기면 널 바이트에서 잘리는 구현이 있으므로 base64나 hex로 인코딩해서 넘긴다. 입력 문자열의 실제 바이트 수가 궁금하면 [해시 생성기](/tools/net/hash-generator/)로 다이제스트 길이를 확인해보면 감이 잡힌다.

## $2a$ · $2b$ · $2y$

해시 문자열 앞의 접두어는 알고리즘 버전이다.

| 접두어 | 유래 | 지금 |
|--------|------|------|
| `$2a$` | 원본(1999) | 일부 구현에 8비트 문자 처리 버그 |
| `$2x$`·`$2y$` | PHP가 버그 대응으로 도입 | PHP 생태계 잔재 |
| `$2b$` | OpenBSD 공식 수정본(2014) | **새로 생성할 때 기본값** |

검증은 대부분의 라이브러리가 접두어를 보고 알아서 처리하므로 기존 `$2a$` 해시를 그대로 둬도 로그인은 된다. 새로 만드는 것만 `$2b$`면 된다.

해시 구조는 이렇게 읽는다.

```
$2b$12$LQv3c1yqBWVHxkd0LHAkCO....
 │   │  └─ 22자 salt + 31자 해시 (base64 변형)
 │   └──── cost = 12
 └──────── 알고리즘 $2b$
```

cost가 해시 안에 들어 있으므로 저장된 해시만 보면 그때 쓴 cost를 알 수 있다. 이게 다음 절의 근거다.

## 무중단으로 cost 올리기

기존 해시를 일괄로 다시 만들 수는 없다. 평문이 없기 때문이다. 대신 **로그인 성공 순간에는 평문이 손에 있다.** 그때 재해시한다.

```js
const TARGET_COST = 12;

if (await bcrypt.compare(password, user.hash)) {
  if (bcrypt.getRounds(user.hash) < TARGET_COST) {
    user.hash = await bcrypt.hash(password, TARGET_COST);
    await user.save();
  }
  // 로그인 성공 처리
}
```

이러면 활성 사용자부터 순차적으로 올라간다. 로그인하지 않는 계정은 옛 cost로 남지만, 그 계정은 애초에 인증 시도도 없다.

같은 자리에 알고리즘 교체도 얹을 수 있다. Argon2id로 옮길 거라면 `compare`는 bcrypt로, 재해시는 Argon2로 하면 된다.

## bcrypt를 계속 써도 되나

2015년 PHC 우승자는 Argon2다. 신규 시스템이면 Argon2id가 첫 선택지고, 메모리 하드 특성 덕에 GPU 크래킹 저항이 더 좋다.

그렇다고 bcrypt가 깨진 건 아니다. cost를 적절히 잡은 bcrypt는 2026년에도 유효한 선택이다. 다만 **MD5·SHA-1·SHA-256을 비밀번호에 그대로 쓰는 건 논외**다. 그 함수들은 빠르라고 만들었고, 빠른 게 바로 문제다.

| 용도 | 선택 |
|------|------|
| 신규 시스템 비밀번호 | Argon2id |
| 기존 bcrypt 시스템 | cost 재점검 후 유지 가능 |
| 파일 무결성·체크섬 | SHA-256 |
| 비밀번호에 SHA-256 단독 | **쓰지 마라** |

## 정리

- cost는 지수다. +2가 4배다. 설정 숫자 하나를 바꾸기 전에 시간을 잰다.
- 배포 대상 하드웨어에서 직접 측정한다. 남의 벤치마크 값을 그대로 쓰지 않는다.
- 목표 응답 시간(250ms~1s)과 로그인 동시성에서 cost를 역산한다.
- 입력은 72바이트에서 잘린다. 긴 패스프레이즈를 받는다면 SHA-256 + base64로 선처리한다.
- 새 해시는 `$2b$`. 기존 `$2a$`는 검증만 되면 그대로 둬도 된다.
- cost 인상은 로그인 성공 시점 재해시로 무중단 처리한다.
