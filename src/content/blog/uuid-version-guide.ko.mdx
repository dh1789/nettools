## 증상부터

테이블 PK를 `AUTO_INCREMENT`에서 UUID로 바꿨다. 개발 환경에서는 아무 문제 없었다. 운영에서 행이 수천만을 넘어가자 INSERT 지연이 눈에 띄기 시작한다. 조회는 멀쩡한데 쓰기만 느리다. 디스크 IOPS가 삽입량에 비해 과하게 튀고, 버퍼 풀 적중률이 서서히 내려간다.

코드는 그대로다. 데이터만 늘었다. 이 조합이면 UUID 버전 문제다.

## 랜덤 PK가 B-tree에서 하는 일

InnoDB의 클러스터형 인덱스는 PK 순서로 데이터를 물리 정렬한다. PK가 순증가하면 삽입은 항상 마지막 페이지에서 일어난다. 그 페이지 하나만 메모리에 있으면 된다.

UUID v4는 122비트가 난수다. 삽입 위치가 인덱스 전체에 균일하게 흩어진다. 결과가 세 가지로 나타난다.

- **페이지 분할**: 꽉 찬 중간 페이지 한가운데로 값이 들어오면 페이지를 쪼갠다. 쪼개진 두 페이지는 절반씩만 찬다. 같은 행 수를 담는 데 더 많은 페이지가 필요해진다.
- **버퍼 풀 오염**: 삽입마다 다른 페이지를 건드린다. 인덱스가 메모리보다 커지는 순간부터 삽입 하나가 읽기 I/O를 부른다.
- **세컨더리 인덱스 증폭**: InnoDB 세컨더리 인덱스는 리프에 PK 값을 그대로 담는다. PK가 커지면 모든 세컨더리 인덱스가 함께 커진다.

세 번째가 특히 조용하다. 인덱스 3개짜리 테이블이면 PK 한 바이트가 실질적으로 네 바이트다.

## 버전별로 뭐가 다른가

RFC 9562(2024년 5월, RFC 4122 대체)가 v6·v7·v8을 표준으로 추가했다. 실무에서 고를 만한 건 사실상 v4와 v7이다.

| 버전 | 구조 | 시간 정렬 | 랜덤 비트 | 실무 위치 |
|------|------|----------|----------|----------|
| v1 | 60b 타임스탬프 + 14b 클럭시퀀스 + 48b 노드(MAC) | 부분적 | 없음 | 레거시. MAC 노출 |
| v4 | 122b 난수 | 없음 | 122 | 기본값. PK로는 부적합 |
| v6 | v1의 타임스탬프를 상위로 재배치 | 예 | 없음 | v1 마이그레이션 전용 |
| v7 | 48b Unix ms + 74b 난수 | 예 | 74 | **신규 PK 기본 선택** |
| ULID | 48b Unix ms + 80b 난수 | 예 | 80 | Base32 26자, URL 친화 |

v7 비트 레이아웃은 이렇다. 앞 48비트가 밀리초 단위 Unix 타임스탬프고, 그 뒤로 버전(4b) · 난수(12b) · 변형(2b) · 난수(62b)가 붙는다. 상위 비트가 시간순이므로 삽입이 인덱스 오른쪽 끝에 몰린다. AUTO_INCREMENT의 지역성을 되찾으면서 분산 생성도 유지한다.

값을 눈으로 뜯어보려면 [UUID / ULID 생성기](/tools/net/uuid-generator/)에서 버전별로 뽑아 앞자리를 비교하면 된다. v7끼리는 앞 12자리가 시간순으로 증가하고, v4는 매번 무작위다. 그 앞 48비트를 십진수로 바꿔 [Unix 타임스탬프 변환기](/tools/net/unix-timestamp/)에 넣으면 생성 시각이 그대로 나온다.

## v1을 아직 쓰고 있다면

v1의 마지막 48비트는 노드 식별자다. 대부분의 구현이 여기에 NIC의 MAC 주소를 그대로 넣는다. 즉 발급된 UUID를 보면 생성한 장비를 특정할 수 있다.

```bash
# v1 UUID: 6ba7b810-9dad-11d1-80b4-00c04fd430c8
#                                    ^^^^^^^^^^^^ 마지막 12자리 = 노드
```

`00:c0:4f`가 OUI다. [MAC 주소 OUI 조회](/tools/net/mac-oui-lookup/)에 넣으면 제조사가 나온다. 외부로 나가는 식별자에 v1을 쓰고 있으면 인프라 정보를 흘리고 있는 것이다. 랜덤 노드 옵션을 강제하거나 v7로 옮기는 게 맞다.

## 생성

```bash
# macOS/Linux — v4
uuidgen

# Python 3.14+ (v7 내장)
python3 -c "import uuid; print(uuid.uuid7())"

# Python 3.13 이하 — uuid6 패키지
pip install uuid6 && python3 -c "import uuid6; print(uuid6.uuid7())"

# Node.js — v4 (표준 내장은 v4까지)
node -e "console.log(crypto.randomUUID())"

# PostgreSQL 18+
SELECT uuidv7();

# MySQL 8.0 — v1을 정렬 가능하게 저장
SELECT UUID_TO_BIN(UUID(), 1);
```

MySQL은 아직 v7 내장 함수가 없다. `UUID_TO_BIN(uuid, 1)`의 두 번째 인자는 v1의 time-low와 time-high를 스왑해 상위 비트를 시간순으로 만드는 스왑 플래그다. v1을 쓰는 기존 시스템에는 유효한 임시 처방이지만, 노드에 MAC이 박히는 문제는 그대로다. 애플리케이션에서 v7을 생성해 넘기는 쪽이 낫다.

## 저장 타입을 문자열로 두지 마라

버전보다 먼저 확인할 게 있다. UUID를 `CHAR(36)`이나 `VARCHAR(36)`으로 저장하고 있는지.

| 저장 방식 | 바이트 | 1억 행 PK |
|----------|-------|----------|
| `CHAR(36)` | 36 | 3.6GB |
| `BINARY(16)` | 16 | 1.6GB |
| PostgreSQL `uuid` | 16 | 1.6GB |

PK 2GB 차이가 세컨더리 인덱스마다 복제된다. 인덱스 3개면 8GB다. 여기에 비교 연산까지 문자열로 돌아간다.

```sql
-- MySQL: 문자열 → 바이너리
ALTER TABLE orders ADD COLUMN id_bin BINARY(16);
UPDATE orders SET id_bin = UUID_TO_BIN(id);
-- 검증 후 PK 교체

-- 읽을 때
SELECT BIN_TO_UUID(id_bin) FROM orders;
```

PostgreSQL은 `uuid` 타입이 이미 16바이트다. `text`로 넣어둔 컬럼만 `ALTER TABLE ... TYPE uuid USING id::uuid`로 바꾸면 된다.

## 고르는 기준

| 상황 | 선택 |
|------|------|
| 신규 테이블 PK, 분산 생성 필요 | v7 |
| PK가 URL에 노출, 짧아야 함 | ULID (26자) |
| 생성 시각이 노출되면 안 되는 식별자 | v4 |
| 단일 DB, 분산 생성 불필요 | BIGINT AUTO_INCREMENT |
| 기존 v1 시스템 | v6 또는 v7 이관 |

마지막 줄이 중요하다. UUID가 필요 없으면 쓰지 않는 게 가장 빠르다. 단일 DB에서 순번이면 충분한데 "나중에 샤딩할지도"라는 이유로 UUID를 넣는 경우가 흔하다. 그 샤딩은 대개 오지 않고, 인덱스 비용은 첫날부터 발생한다.

## v4에서 v7로 옮길 때

기존 v4 값을 재생성하지 마라. 외부에 나간 식별자는 그대로 두고, 새로 발급되는 것만 v7로 바꾸면 된다. 두 버전은 같은 128비트 공간을 쓰므로 컬럼 타입을 건드릴 필요가 없다. 충돌 위험도 사실상 없다 — 버전 니블 자체가 다르다.

정렬 이점은 새로 들어오는 행부터 적용된다. 기존 인덱스의 단편화는 남으므로, 여유가 있으면 `OPTIMIZE TABLE`(MySQL)이나 `REINDEX`(PostgreSQL)로 한 번 정리한다. 둘 다 테이블 잠금이 걸리므로 트래픽 낮은 시간대에 한다.

## 정리

- 쓰기가 느려지는 UUID PK는 대개 v4의 랜덤 삽입 위치가 원인이다.
- v7은 상위 48비트가 시간순이라 삽입 지역성을 회복한다. 신규 PK의 기본값으로 삼는다.
- v1은 MAC 주소를 노출한다. 외부 식별자로 쓰고 있으면 지금 확인한다.
- 버전보다 먼저, 문자열 저장부터 `BINARY(16)`으로 바꾼다.
- UUID가 꼭 필요한지부터 따진다. 필요 없으면 순번이 항상 빠르다.
