## 증상부터

인증 앱에 뜬 6자리를 그대로 입력했는데 "잘못된 코드"가 뜬다. 오타가 아니다. 다시 시도해도 같다. 어제까지는 됐고, 앱을 다시 설치하지도 않았다. 같은 계정을 다른 기기에 등록해두었다면 그쪽 코드는 통과한다.

이 조합이면 시크릿 문제가 아니다. 시계다.

## TOTP는 시각을 입력으로 받는다

TOTP(RFC 6238)는 HOTP의 카운터 자리에 시간을 넣은 것이다. 계산은 이렇게 돌아간다.

```
T = floor((현재 Unix 시각 - T0) / X)      # T0 = 0, X = 30초가 기본
code = 동적절단(HMAC-SHA1(secret, T)) mod 10^6
```

입력이 셋뿐이다 — 시크릿, 알고리즘 파라미터, 그리고 T. 시크릿은 등록 후 안 바뀐다. 파라미터도 고정이다. **남는 변수는 T 하나고, T는 시계에서 나온다.**

30초 스텝이므로 클라이언트와 서버의 시각이 30초 이상 어긋나면 서로 다른 T를 쓰고, 결과 코드가 달라진다. 에러 메시지는 "잘못된 코드"뿐이라 원인이 안 보인다.

지금 내 타임스텝이 몇인지는 이렇게 본다.

```bash
# 현재 타임스텝 (30초 기준)
python3 -c "import time; print(int(time.time()) // 30)"

# Unix 시각 자체
date +%s
```

이 값을 [Unix 타임스탬프 변환기](/tools/net/unix-timestamp/)에 넣으면 사람이 읽는 시각으로 확인할 수 있고, [TOTP 코드 생성기](/tools/net/totp-generator/)에 같은 시크릿을 넣어보면 앱이 만든 코드와 대조된다. 두 코드가 다르면 시각 차이가 확정이다.

## 시각 확인과 교정

```bash
# Linux — 동기 상태와 오차
timedatectl status
chronyc tracking          # chrony: "System time" 항목이 오차
ntpq -p                   # ntpd: offset 열(ms)

# macOS — 강제 동기
sudo sntp -sS time.apple.com

# Windows
w32tm /query /status
w32tm /resync
```

`chronyc tracking`의 System time 값이 수십 ms면 정상이다. 초 단위로 벌어져 있으면 그게 원인이다.

가상머신과 컨테이너는 특히 잘 밀린다. 호스트가 절전에서 깨어난 뒤 게스트 시계가 따라오지 못하는 경우, 그리고 컨테이너가 호스트 시계를 그대로 쓰는데 호스트에 NTP가 안 붙은 경우가 흔하다. 스마트폰은 "자동 날짜 및 시간"을 끄고 수동으로 맞춰둔 상태가 범인이다.

## 서버 쪽 window

서버는 보통 앞뒤 몇 스텝을 함께 허용한다. 이걸 window라고 한다.

| window | 허용 범위 | 성격 |
|--------|----------|------|
| 0 | 현재 스텝만 | 시계가 조금만 밀려도 실패 |
| 1 | ±30초 | **기본 권장값** |
| 2 | ±60초 | 관대함. 재사용 공격 표면 증가 |
| 10 | ±5분 | 사실상 시간 검증 포기 |

window를 키우면 실패는 줄지만 탈취된 코드의 유효 시간도 같이 늘어난다. 로그인 실패가 잦다고 window부터 올리는 건 증상을 덮는 처방이다. 시계를 맞추는 게 먼저다.

## 스텝 경계 함정

코드 유효기간이 30초라고 해서 화면에 뜬 30초 내내 안전한 건 아니다. 스텝 경계는 절대 시각(`unixtime % 30 == 0`)에 걸린다. 남은 시간이 2~3초일 때 입력을 시작하면, 전송·처리 사이에 경계를 넘어 서버는 다음 스텝으로 검증한다. window가 0이면 그대로 실패다.

남은 시간이 5초 미만이면 다음 코드를 기다리는 게 맞다. 자동화 스크립트라면 코드 생성 직후 남은 시간을 계산해서 임계값 이하일 때 대기시킨다.

```bash
# 현재 스텝의 남은 초
python3 -c "import time; print(30 - int(time.time()) % 30)"
```

## 시계가 맞는데도 실패한다면

파라미터 불일치다. `otpauth://` URI에 다 들어 있다.

```
otpauth://totp/MyService:user@example.com?secret=JBSWY3DPEHPK3PXP&issuer=MyService&algorithm=SHA1&digits=6&period=30
```

| 파라미터 | 기본값 | 어긋날 때 증상 |
|----------|--------|---------------|
| `algorithm` | SHA1 | 서버가 SHA256인데 앱이 SHA1 → 항상 실패 |
| `digits` | 6 | 8자리 발급인데 6자리 입력 → 항상 실패 |
| `period` | 30 | 60초 서버에 30초 앱 → 절반쯤 우연히 통과 |
| `secret` | — | Base32. 소문자·공백·패딩 `=` 처리 차이 |

`period`가 다를 때가 가장 헷갈린다. 두 스텝에 한 번꼴로 우연히 맞아떨어져서 "가끔 되는데 자주 틀린다"로 보인다. 시간 오차와 증상이 비슷하지만 시계를 맞춰도 안 고쳐진다.

Base32 시크릿은 대소문자를 구분하지 않고 패딩 `=`도 대개 생략한다. 다만 구현에 따라 공백을 그대로 디코딩에 넘겨 깨지는 경우가 있으니, 앱에 붙여넣을 때 앞뒤 공백을 지운다.

QR로 등록할 때 위 URI가 그대로 인코딩된다. 발급 화면의 QR이 의심스러우면 [QR 코드 생성기](/tools/net/qr-code-generator/)로 같은 URI를 만들어 대조하면 파라미터 누락이 드러난다.

## 진단 순서

1. 앱과 서버의 Unix 시각을 각각 확인한다. 차이가 30초 이상이면 여기서 끝이다.
2. 시계를 NTP로 강제 동기하고 다시 시도한다.
3. 여전히 실패하면 코드 남은 시간이 5초 이상인 상태에서 재시도한다.
4. 그래도 실패하면 `algorithm`·`digits`·`period`를 발급 측 문서와 대조한다.
5. 전부 맞는데 실패하면 시크릿이 재발급됐는지 확인한다. 계정 복구나 2FA 재설정 과정에서 조용히 바뀐다.

## 백업 코드부터 챙겨라

시계가 밀린 기기 하나에 2FA를 몰아두면 그 기기가 잠기는 순간 계정도 잠긴다. 등록 시점에 받은 백업 코드는 시간과 무관하게 동작하니 별도 보관한다. 시크릿(또는 QR)을 안전한 곳에 따로 저장해두면 다른 기기에 재등록할 수 있다.

## 정리

- TOTP 실패의 대부분은 시크릿이 아니라 시각 오차다. 30초 스텝을 넘기면 다른 코드가 나온다.
- `chronyc tracking` / `w32tm /query /status`로 오차를 먼저 확인한다. 초 단위면 그게 원인이다.
- window를 올려 덮지 마라. ±30초(window 1)가 기준선이다.
- 남은 시간 5초 미만이면 다음 코드를 기다린다. 경계는 절대 시각에 걸린다.
- 시계가 맞는데 실패하면 `algorithm`·`digits`·`period` 불일치를 본다. `period` 불일치는 "가끔 되는" 증상으로 나타난다.
